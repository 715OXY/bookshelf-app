## 認可の構成

既存BookPolicyとAuthServiceProviderの登録を再利用する。
API Controllerのstore・update・destroyから$this->authorize()を呼ぶ。
所有者の判定をControllerへ直接記述していない。

更新FormRequestはController本体より先に評価される。
このためUpdateBookRequest::authorize()でもBookPolicyを呼び、
非所有者に入力検証結果を返す前に拒否する。
Controller側にも保存処理直前の認可を維持する。

共通ApiFormRequest・公開GETの認証条件は変更していない。
登録者自動設定・外部user_id指定拒否はIssue #68の実装を維持する。

## 応答順序とデータ保護

PUT・DELETEでは次の順序を確認した。

1. 未認証は対象の有無にかかわらず401。
2. 有効Bearerで対象不存在なら404。
3. 対象が存在しても非所有者なら403。PUTの入力不備より認可を優先する。
4. 所有者のPUT入力不備は422、正常更新は200、正常削除は204。

Acceptヘッダー省略時もJSONとなり、Locationヘッダーを返さない。
debug有効時も401・403・404はmessageのみのJSONとした。
403では項目別入力エラーや内部例外情報を返さない。

拒否時は業務7テーブルの状態保持を確認した。
正常更新では所有者・レビュー・いいね・お気に入り等を保持し、
ジャンルを同期する。正常削除では対象の関連データを削除し、
会員・ジャンルマスタ・無関係な書籍とそのジャンル紐付けを保持する。
